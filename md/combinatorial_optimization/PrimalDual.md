s から t へ、費用の安い道から順に流す最小費用流です。流す量ごとの費用の最小 (slope) を返せます。流したあとに頂点や辺を足して、続けて流せます。

```cpp
template <class Flow, class Cost> class PrimalDual;
explicit PrimalDual(int n = 0);
int add_vertex();
int add_edge(int from, int to, Flow cap, Cost cost);
std::pair<Flow, Cost> flow(int s, int t);
std::pair<Flow, Cost> flow(int s, int t, Flow limit);
std::vector<std::pair<Flow, Cost>> slope(int s, int t);
std::vector<std::pair<Flow, Cost>> slope(int s, int t, Flow limit);
struct Edge { int from, to; Flow cap, flow; Cost cost; };
Edge get_edge(int i) const;
std::vector<Edge> edges() const;
std::vector<long long> potential();
int size() const;
```

頂点は 0 から n - 1 の番号で、`add_vertex()` で 1 つ足せます。`add_edge` は、from から to へ容量 cap、1 単位あたりの費用 cost の辺を足し、足した順の番号 (0 から) を返します。費用は負でもかまいません。ただし、流す時点の残余グラフに負閉路 (費用の和が負の閉路) があってはいけません。負の費用の辺があっても、網が DAG なら大丈夫です。名前と意味は、ACL の mcf_graph にあるものはそれに合わせています。

`flow(s, t, limit)` は、今の流れから続けて s から t へ limit まで流せるだけ流し、増えた流量と費用を返します。費用は、その流量を増やすときの最小です。`slope(s, t, limit)` も同じく流し、増やした量 x ごとの費用の最小 g(x) の折れ線の折れ点を、(0, 0) から x の昇順に返します。g は下に凸で、傾きの同じ点は含めません。最後の点が、増えた流量と費用です。どちらも何度呼んでもよく、s と t は呼ぶたびに変えてかまいません。

流したあとに頂点や辺を足すこともできます。そのときは、足したあとの網でも、今の流れはその流量での最小費用でなければなりません (残余グラフに負閉路があってはいけません)。足す辺が今の流れより安い迂回を作ると、この条件が崩れます。料理人ごとに次の枠を足していく NOI2012 美食节や、元の網を流し切ってから費用付きの辺を足す洛谷 P2604 网络扩容のような使い方では崩れません。

`get_edge(i)` と `edges()` で辺ごとの流量を、`potential()` でポテンシャル p を取り出せます。p は相補性を満たします。容量の残る辺では縮約費用 cost + p[from] - p[to] が 0 以上で、流れのある辺では 0 以下です。費用の和を最大にしたいときは、費用の符号を反転して渡し、返った費用の符号を戻します。

`Flow` と `Cost` は整数の型です。(頂点の数) × (費用の絶対値の最大) が $2^{62}$ に収まり、流した量と費用の和が `Flow` と `Cost` に収まる必要があります。この型は、折れ線の区間ごとに Dijkstra を 1 回回すので、区間が多いと時間がかかります。下限付きの辺や湧き出しのある網 (b-flow) と、容量が大きく区間の多い網には、[最小費用流](MinCostFlow.md) を使ってください。

## 中身

primal-dual 法です。ポテンシャルで縮約した費用について、s からの最短路を Dijkstra (radix heap) で求めます。そのあと、縮約費用が 0 になった弧だけの網で流せるだけ流すことを繰り返します。

Dijkstra は、t を取り出したあとも、t と同じ距離の頂点を取り出し終えるまで続けます。t から出る弧は緩和しません。取り出した頂点だけポテンシャルを動かすので、縮約費用 0 の網は、s から t への最短路をすべて含みます。流すときは、まず Dijkstra の最短路木の道に流します。次に、縮約費用 0 の網で t から逆向きの BFS をして段数を付け、段数が 1 ずつ減る弧だけを使う DFS (Dinic) で流すことを、s に段数が付かなくなるまで繰り返します。その距離の道がすべて流れるので、Dijkstra 1 回が折れ線のちょうど 1 区間になります。距離がみな違う網では、最短路木の道のほかに同じ距離の道が無いので、BFS はそれを確かめる 1 回で済みます。逆向きの BFS は t へ届く頂点しか歩かず、縮約費用が 0 の弧でだけ相手の弧の容量を読みます。

ACL の mcf_graph は、Dijkstra 1 回ごとに最短路を 1 本だけ流します。縮約費用 0 の弧でたどった頂点は、ヒープを通さず、積んだ順に取り出します。そのため、容量の大きい密な網では道が長くなって、1 本で流せる量が小さくなります。頂点 300 の完全グラフ (容量 $10^6$、費用 100 以下) では、Dijkstra が 20 万回を超えました。この型は、同じ距離の道をまとめて流すので、どの網でも Dijkstra の回数が折れ線の区間の数と同じになります。

初めの負の費用と、あとから足した辺で縮約費用が負になったときは、流す前にポテンシャルを直します。残余グラフが DAG なら位相順に、そうでなければキューを使う Bellman-Ford で直します。あとから足した頂点のポテンシャルは、古い頂点から入る弧の端の値で決めます。

辺は、初めの `flow` か `slope` で CSR に組みます。そのあと足した辺の弧は、端の頂点の区画の後ろに置きます。区画に空きが無ければ、その頂点の弧を倍の大きさの区画にして配列の末尾へ移します。辺を足しながら少しずつ流す使い方でも、呼ぶたびに組み直しません。頂点ごとのポテンシャルと距離は 16 byte の組にして、Dijkstra で辺 1 本を見るときに読む場所を 1 か所にしています。

方式は procon-judge の self-flow-mincostflow-slope で比べて選びました。性質の違う 9 つの族の 12 ケースで、ACL の mcf_graph の写しと比べた計算の部分の時間は次のとおりです。どれも同じ回の同じ CPU (EPYC 7763) の x64-gcc で測りました。

| 網 | この型 | ACL の写し |
| --- | ---: | ---: |
| 費用の種類が少ない割り当て (ABC 247 G の形、左右 2000) | 22 ms | 179 ms |
| 費用が 0 か 1 の格子のマッチング (CF 316C2 の形、80 × 80) | 5.6 ms | 74 ms |
| 頂点 300 の完全グラフ (容量 $10^6$) | 234 ms | 10 秒超 |
| 区間の K 重の詰め込み (鎖 10 万、K = 100) | 683 ms | 685 ms |
| 費用の大きい割り当て (左右 3000) | 740 ms | 807 ms |
| 乱択の網 (頂点 2 万、辺 20 万) | 446 ms | 390 ms |

いちばん離されたのは乱択の網で、1.15 倍でした。LOJ 102 (頂点 400、辺 15000 の最小費用最大流) では、この型が 42 ms、[最小費用流](MinCostFlow.md) の cost scaling が 13 ms でした。slope を使わない問題で、折れ線の区間の多い網なら、最小費用流の型のほうが速いこともあります。記録は algo-notes の notes/network-flow.md にあります。
