二部グラフのマッチングを、呼ぶ側が決めた順に増加路を 1 本ずつ探して大きくします。左の頂点を足す順で答えが決まる問題 (値を小さい順に足し、増加路が見つかった値を採る貪欲法など) と、辺を足し引きしながら最大マッチングを保つ問題のための型です。一度に最大マッチングを求めるだけなら、BipartiteMatching のほうが速く解けます。

```cpp
class IncrementalBipartiteMatching;
IncrementalBipartiteMatching(int l, int r, const std::vector<std::array<int, 2>>& edges = {});
void add_edge(int a, int b);
void erase_edge(int a, int b);
bool augment(int a);
bool augment();
int size() const;
int mate(int v) const;
```

左の頂点 l 個と右の頂点 r 個と、辺 (左 a、右 b) の列を受けます。多重辺があってもかまいません。頂点の番号は BipartiteMatching と同じく、左 a を a、右 b を l + b とします。マッチングは空で始め、`augment` を呼んだときだけ 1 本ずつ大きくします。

- `add_edge(a, b)` は、左 a と右 b を結ぶ辺を足します。マッチングは変えません。
- `erase_edge(a, b)` は、左 a と右 b を結ぶ辺を 1 本抜きます。無ければ何もしません。抜いた辺の組がマッチングに入っていて、同じ組を結ぶ辺がほかに無ければ、両端が空きます。手間は a の次数に比例します。
- `augment(a)` は、空いた左 a から増加路を探し、見つかれば流して true を返します。a が空いていないときと、a から増加路が無いときは false です。
- `augment()` は、空いた左の頂点のどれかから増加路を探し、見つかれば 1 本だけ流して true を返します。false なら今のマッチングは最大です。
- `size()` はマッチングの辺の数、`mate(v)` は頂点 v の相手 (いなければ -1) です。

辺を 1 本足すか抜くかで変わる最大マッチングの大きさは、高々 1 です。最大マッチングを保ちながら辺を足し引きするときは、足すか抜くたびに `augment()` を 1 回呼べば足ります。

使い方の例です。

- 値 1, 2, ... の順に使えるところまで使う問題 (洛谷 P1640、LOJ 2338) は、`while(k < V && m.augment(k)) ++k;` と書きます。
- 候補を小さい順に足して増加路が見つかった候補を採る問題 (CF 1728F) は、候補を左の頂点にして、小さい順に `augment(v)` を呼びます。見つからない探索が大半でも、下の印のおかげで、見つからない探索は合わせて辺の数の手間で済みます。
- 辺を足しながら mex を伸ばす問題 (CF 1139E) は、`add_edge` のあとに、今の mex の値から `augment` を呼び続けます。
- 辺を切り替えるたびに完全マッチングがあるかを答える問題 (AOJ 3198) は、`add_edge` か `erase_edge` のあとに `augment()` を 1 回呼び、`size()` を見ます。
- 頂点 v がどの最大マッチングにも入るかを、頂点を消しながら調べる問題 (洛谷 P1971) は、v に付いた辺を全部 `erase_edge` で抜いてから `augment()` を呼びます。v に相手がいて、増加路が見つからなければ、v はどの最大マッチングにも入ります。

## 中身

隣接は 1 本の配列の上に、左の頂点ごとの区画として置きます。構築で渡した辺は CSR と同じ並びにし、`add_edge` で区画が溢れたら、2 倍の大きさの区画を配列の末尾に取って写します。`erase_edge` は、区画の中で抜く辺を末尾の辺と入れ替えます。

増加路は幅優先で探し、隣の右の頂点を見るたびに空いているかを確かめます。増加路が見つからなかった探索で訪ねた左の頂点の集合 D には印を残し、次からの探索では D に入りません。D の頂点の隣の右の頂点はどれも埋まっていて、その相手も D にあるので、D からは空いた右の頂点へ届かないためです。D の外を通る増加路は D の頂点の隣を通らないので、流したあとも D の頂点の隣と相手は変わりません。そのため、増加路が見つかっても D の印は消さず、見つかった探索で訪ねた頂点の印だけを消します。D の頂点から辺を足したときと、D の頂点が使っている辺を抜いたときは、印を全部消します。

procon-judge の 6 問で書き比べました。x64-gcc の値です (アルゴリズムの時間の最大、run 44303513435)。この形と、増加路が見つかるたびに印を全部消す形 (bfs)、探すたびに印を消す教科書の形 (reset) と、今の Library で書いた形を並べています。今の Library には増加路を 1 本ずつ探す口が無いので、二部マッチングを二分探索するか、前のマッチングを渡して解き直しています。

| 問題 | 大きさ | この形 | bfs | reset | 今の Library |
| --- | --- | --- | --- | --- | --- |
| cf-1728-f (EPYC 7763) | 値 10^6 個、辺 10^6 本 | 50.0 ms | 98.8 ms | 661.8 ms | なし |
| luogu-P1640 (Xeon 6975P-C) | 辺 2 × 10^6 本 | 15.6 ms | 19.7 ms | 414.6 ms | 234.4 ms |
| cf-1139-e (EPYC 7763) | 辺 5000 本を足しながら | 4.17 ms | 4.00 ms | 8.58 ms | 88.9 ms |
| aoj-3198 (Xeon 6975P-C) | 辺の切り替え 5000 回 | 56.6 ms | 47.9 ms | なし | 234.3 ms |

cf-1728-f は、見つからない探索の印を、増加路が見つかっても消さないことが効きます。2 の冪の a のケースでは、見つかるたびに消す形が、増加路が見つかった探索で消した頂点をもう一度訪ねるので遅くなります。aoj-3198 と cf-1139-e は、x64-gcc ではこの形が bfs より遅く出ました。x64-clang と arm-clang では、どちらの問題もこの形が最も速く、aoj-3198 の x64-clang は 53.3 ms (bfs は 71.3 ms) です。増加路を高々 1 本探す aoj-3198 専用の形 (dyn) は 47.1 ms でした。

2 MB 以上の配列は、Linux では 2 MB の区画 (huge page) に置き、先頭を配列ごとにずらします (MaxFlow と同じ allocator)。探索の待ち行列と、頂点を見つけた左の頂点の表は 0 で埋めず、使うところまでしかページに触りません。この 2 つを入れる前の版 (配列を普通に確保して 0 で埋める形) と、同じ回 (run 44300849581) で比べた値です。値が 10^6 個ある cf-1728-f と、辺が 2 × 10^6 本ある luogu-P1640 で縮みました。

| 問題 | huge page に置く形 | 前の版 |
| --- | --- | --- |
| cf-1728-f (最大のケース、x64-gcc、EPYC 9V45) | 31.8 ms | 37.9 ms |
| cf-1728-f (最大のケース、arm-gcc、Neoverse-N2) | 30.1 ms | 39.9 ms |
| luogu-P1640 (最大のケース、x64-gcc、Xeon 6975P-C) | 21.1 ms | 23.9 ms |
| luogu-P1640 (最大のケース、arm-gcc、Neoverse-N2) | 13.7 ms | 18.1 ms |

luogu-P1640 の reset は、空いた右の隣を先に探さない深さ優先なので、道の形のケースで増加路を 1 本探すたびに道の端まで下ります。幅優先なら、隣の空いた右の頂点をすぐに見つけます。luogu-P1640 の時間の大半は辺の列と隣接の配列を組む分で、マッチングを使わない併査集の別解は 3.2 ms です (表と同じ回)。記録は algo-notes の notes/network-flow.md にあります。
